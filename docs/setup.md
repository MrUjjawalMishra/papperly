# Setup and operations

Use Node 24/npm and `npm ci`. Run `npm run verify`, `npm run format:check`, and `node scripts/scan-secrets.mjs`. Unit/database tests are self-contained embedded PostgreSQL; the Worker build is a dry run. `npx tsx scripts/local-load.ts` runs the labelled single-connection diagnostic exercise and rewrites docs/local-load-evidence.json with measured results.

For a fresh local Supabase development stack, install the official CLI and Docker following provider guidance, inspect supabase/config.toml, then start/reset **only the disposable development instance**. Never use reset against staging/production. All SQL migrations are ordered and required; seed.sql runs only after the full migration chain. The schema includes private SECURITY DEFINER helpers resolved when operations execute, so no application traffic should be admitted during an initial incomplete schema installation. No downgrade scripts are supplied.

Managed staging setup requires exact environment identity and secure values from .env.example. See deployment.md. Alias-domain control, disabled signup, administrator-only account creation, Worker session encryption and permitted HTTPS origins are release prerequisites. PostgREST must expose public only; private must not be an exposed API schema. Keep service-role key server-side. Do not use it for ordinary role acceptance tests.

Bootstrap the first owner with the restricted `node scripts/bootstrap-owner.mjs` server administration script. Supply OWNER_BOOTSTRAP_USER_ID, OWNER_BOOTSTRAP_PASSWORD, OWNER_BOOTSTRAP_DISPLAY_NAME, AUTH_ALIAS_DOMAIN and SUPABASE_SERVICE_ROLE_KEY through the secure execution environment; never put their secret values in SQL, source or chat. The script refuses to reset or reissue an existing active owner and verifies Auth identity before linking membership. It compensates only a newly created Auth identity after a definite database failure, probing ambiguous outcomes first. OWNER_USER_ID can pin the Worker lookup; when omitted, service-only lookup uses the single active owner. Inactive historical owner IDs remain for attributed audit records. Verify separate owner login after bootstrap; ordinary parent-role creation then proceeds through the API. Routine staging acceptance uses disposable synthetic owners and leaves no usable owner account. Owner recovery requires explicit operational authorization, recent administrator identity verification, forced application/provider-session revocation and an incident/audit record; no public recovery endpoint exists.

AI and scanner adapters implement private HTTPS gateway contracts, not selected provider products. AI requests include task/model/promptVersion/evidence and expect schema-valid JSON (see contracts). Requests have 20-second timeouts, a four-claim outbox retry bound, idempotency key and per-school quota reservations. Scanner requests contain private bytes, SHA-256 and a dedup key; response must be `{checksum,verdict: clean|infected}`. Missing configuration leaves AI unavailable and attachments quarantined/unavailable. Evaluate selected providers, privacy terms, model quality and scanner file corpus before enabling real data.

Retention is provisional: academic year plus 90 days, audit metadata 12 months, raw imports completion plus 24 hours, prepared exports 24 hours. Current parser does not store raw XLSX files; redacted row outcomes persist. Exports expire and scheduled cleanup deletes R2 objects. Full school-approved deletion/tombstone/cached-search/backup reapplication workflow remains unfinished and must not be enabled by assuming school consent. Deactivation preserves history. Never promise previously downloaded copies can be recalled.

Operational recovery:

- Outbox dispatched/processing leases recover after timeout. Completed jobs deduplicate; stale run tokens cannot commit generic job results. Inspect failed/unavailable state and error code without private payloads. Do not bypass review or RLS to clear a job.
- Auth provisioning retries reserve the same UUID. Existing Auth users are inspected, not reset. After Auth succeeds and database activation fails, retry activation; an issued credential response lost in transit requires an authorized reset. Scheduled reconciliation now activates reserved Auth identities that exist; missing Auth identities stay reserved for an explicit authorized retry/reset, never silently recreated with an undisclosed credential.
- R2 upload failure leaves quarantine metadata/quota reserved. Scheduled reconciliation repairs lost completion and releases quota for missing objects after 24 hours; do not manually mark an unscanned object clean.
- If a migration partially fails, inspect migration history and actual objects, determine transaction outcome, then forward-fix. Do not rerun destructive SQL or drop a live schema.
- Worker rollback requires compatibility with current schema; capture the previous successful deployment ID first. Backup/restore rehearsal is required before real student data and has not been completed.
