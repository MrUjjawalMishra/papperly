## Staging release process

1. Configure secure environment bindings listed in .env.example. Verify exact Cloudflare account and Supabase project against the intended organization/environment. Update docs/staging-target.json only with verified identifiers; it is intentionally `verified: false` now.
2. Review budget before creating any paid resource. Inspect/reuse private staging R2 bucket, Queue and Worker; do not blindly create duplicates. Confirm R2 has no public access and assign least-privilege Worker/Queue/R2 credentials. Separate development, staging and production resources and keys.
3. Configure Supabase Auth: public signup/anonymous disabled, immutable alias domain, initial owner created through restricted administrative setup. Generate a unique session key using a secure secret mechanism. Place Worker secrets with Wrangler secrets/settings, never committed .dev.vars. Set permitted HTTPS origins explicitly. Separate staging and production keys.
4. Feature branch validation runs lint, format, TypeScript, PostgreSQL/RLS tests, Worker dry-run build, frontend absence and secret-pattern checks. Staging workflow repeats these gates, including gitleaks, before accessing environment-scoped deployment credentials. PR code receives no deployment secrets.
5. Automatic trigger is a push to proposed `staging` branch with environment-scoped `ENABLE_STAGING_AUTODEPLOY=true`. This is not enabled or tested yet. No merge to main/staging is part of this task. Environment identity guard fails closed while targets are unknown. Per-environment workflow concurrency is serialized and does not cancel an in-progress migration.
6. Supabase CLI links the verified project, previews pending migrations, then applies additive migrations. Canonical local filenames now match the versions assigned by MCP; do not reapply the original pre-normalization filenames. Review actual migration history for drift/partial failure before retries. Never reset/drop the database to resolve drift. Deploy the same immutable commit using Wrangler; release SHA is included in health/readiness. Do not run a second direct deployment while CI is deploying it.
7. Poll GitHub workflow/provider to terminal status. Health/readiness/SHA/anonymous-denial script is only a basic smoke gate. Before declaring integration-verified, run the full multi-role synthetic workflow, cross-school denial, current-membership file download, Queue redelivery/recovery, scheduled expiry/reminders, AI/scanner separately, and 50-examinee mixed load.
8. Record URL, Cloudflare deployment ID, commit SHA, migration versions, workflow run, test measurements, failures, previous known-good release, and recovery decision. Supabase migration versions and SQL verification are recorded; Worker release details remain unavailable. Do not call a successful push or dry-run a successful deployment.
